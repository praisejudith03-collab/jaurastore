## Hard constraints (unchanged)

* Do **not** enable RLS on `public.products`. The storefront keeps an anon-key
  Realtime subscription on it for live stock; RLS without a policy silently
  stops those events. The advisor listing "RLS Disabled in Public -
  public.products" is deliberate. Query 4 locks only `product_variants`,
  `product_prices` and `product_options`.
* Never use the SQL editor's green **Run and enable RLS** button on these
  files. The answer is always **Run without RLS**.
* Never run `supabase_schema.sql` as a whole; sections 15/16 and the image
  migration stay on hold.
* Do not act on the "Duplicate Index" advisories (`admin_reset_tokens`,
  `product_reviews`, `receipts`): older than this migration, performance hints.
* Never request, print or store API keys, passwords, database URLs or
  service-role keys. `SUPABASE_URL` and the service key are server-side only.
* Never reuse a tombstoned product id - the trigger refuses it, by design.

## What is left to do (optional, owner's call)

The **live delete test has still not been run**. It is the only step that
proves the delete path against the real project, and it is safe: it creates a
disposable product, deletes it, and checks the outsides. Steps are in
`MIGRATION_COPY_PASTE.md` and in fine detail in
`STAGING_HARD_DELETE_RUNBOOK.md`:

1. In `/admin`, create a disposable product: id `jau-staging-<timestamp>`,
   name "DELETE ME ...", one dummy photo, `online` off.
2. Delete it through `/admin`. Expect `ok: true`, `deleteMode: "supabase-hard"`,
   `filesRemoved: 1`, the old photo URL 404ing, one row in
   `public.deleted_products`, and no child rows.
3. Never delete a real product, and never reuse the id.

`tools/staging_delete_check.py` (or the `staging-schema-migration.yml`
workflow with `live_purge_check = true`) does all of that in one run.
